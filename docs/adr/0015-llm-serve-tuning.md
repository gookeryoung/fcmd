# 0015 llmserve 启动参数调优策略

- 状态：已落地（auto / default / throughput / long-context / low-vram）
- 日期：2026-11-11
- 关联：`src/fcmd/tools/llm/_llmtune.py`、`llmserve`、`llmservew`、0013（GUI 技术路线）

## 背景

`llmserve` / `llmservew` 原先固定使用一套启动参数：`-np 1`、`--flash-attn on`、
`-ctk/-ctv` 跟随档位、`-b 4096`、`-ub` 跟随档位、`--cache-reuse 256`。这组参数在
单请求、显存充足时表现稳定，但缺少按使用方式的入口：

- 多用户 / 客户端并发时只有一个槽位，请求排队，聚合吞吐上不去。
- 128K 上下文用 f16 KV 会超出 32GB 显卡，只能手工在“额外参数”里拼 `-ctk q8_0`。
- 显存不足时没有一键降级路径，容易直接 OOM。
- 社区常见的“调大 batch / 线程”“开投机解码”等做法缺少本机数据支撑，盲目照搬可能更慢。

因此需要一组**可解释、可回退、默认行为不变**的内置策略，并先用基准测试确定取值。

## 基准方法

- 机器：NVIDIA GeForce RTX 5090 D 32GB（32607 MiB）、Intel Core Ultra 9 285K（24C/24T）、Windows。
- 引擎：llama.cpp `b12212`；模型：`Qwen3-Coder-30B-A3B-Instruct-Q5_K_M`（20.2 GB）。
- 每个配置独立启动 `llama-server`（端口 18080），场景：短对话（输出 128）、长输出（512）、
  代码补全（输入约 1K / 输出 256）、8K 与 32K 长上下文、4 路并发短对话。
- 每轮请求使用唯一 nonce 前缀，避免 KV 前缀缓存命中；取 3–5 轮中位数；预填充 / 解码速度取
  服务端 `timings.prompt_per_second` 与 `timings.predicted_per_second`。
- 缓存对照：`--cache-reuse 0` 与默认 256 的 8K 预填充分别为 16.05k / 16.20k t/s，
  说明重复请求未显著抬高基线，下面的对比有效。
- 下表单位均为 token/s；“并发聚合”= 4 路请求完成 token 总数 / 墙钟时间。

### 1. batch / ubatch / 线程 / KV 类型（单请求）

| 配置 | 代码预填充 1K | 8K 预填充 | 32K 预填充 | 短解码 | 32K 解码 |
|---|---|---|---|---|---|
| 默认 `b4096 / ub2048` | 15.7k | **16.2k** | **9.78k** | **250** | **158** |
| `b2048 / ub512` | 10.0k | 11.5k | 7.68k | 262 | 152 |
| `b4096 / ub1024` | 12.1k | 14.2k | 8.80k | 249 | 152 |
| `b8192 / ub2048` | 14.6k | 14.9k | 9.27k | 248 | 146 |
| `-t 24 -tb 24` | 14.1k | 15.2k | 9.42k | 235 | 140 |
| KV `q8_0` | 13.8k | 14.9k | 9.14k | 214 | 114 |

结论：`ub 2048` 明显优于 512 / 1024；继续放大 batch、把线程从 8 提到 24 都没有收益，
反而在部分场景下降；KV `q8_0` 会用解码速度换显存。因此默认策略保持现状。

### 2. 并发与投机解码

| 配置 | 4 路并发聚合 | 单请求短解码 | 8K 预填充 |
|---|---|---|---|
| `-np 1`（默认） | 150 | **250** | **16.2k** |
| `-np 4` | 300 | 228 | 15.3k |
| `-np 4 --threads-http 8` | **358** | 244 | 15.5k |
| `-np 1 --spec-type ngram-simple` | 170 | 242（长输出 232） | 14.6k |

结论：4 槽 + 8 个 HTTP 线程把并发聚合吞吐提到约 **2.4 倍**，单请求仅下降约 2.5%；
`ngram-simple` 投机解码在本模型的通用代码 / 对话负载上解码反而下降约 11%，不纳入预设。

### 3. 低显存与 128K 上下文

| 配置 | 8K 预填充 | 32K 预填充 | 短解码 | 32K 解码 | 加载 |
|---|---|---|---|---|---|
| KV `q4_0` + `b2048 / ub512` | 14.0k | 8.92k | 198 | 109 | 13.6s |
| `ctx 131072` + KV `q8_0` | 14.5k | 9.11k | 224 | 119 | 12.5s |

结论：省显存策略能以约 14% 预填充、24% 解码损失换取更小 KV；128K + `q8_0` 可正常加载，
32K 解码比 f16 低约 25%，属于可接受的显存换长度取舍。

## 决策

### 1. 内置五个策略，默认行为不变

| 策略 | 关键参数 | 适用场景 |
|---|---|---|
| `auto` | 按显存 / 上下文选择下列预设 | 窗口与 CLI 的默认入口 |
| `default` | `b4096 / ub 档位 / np1 / cr256 / fa on` | 单请求、显存充足（与改造前完全一致） |
| `throughput` | `np4 / --threads-http 8` | 多客户端并发 |
| `long-context` | KV `q8_0`，其余同默认 | 128K 上下文 |
| `low-vram` | KV `q4_0`、`b2048 / ub512`、`cr128` | 显存不足或超长上下文放不下 q8 KV |

策略只负责“建议值”，显式填写的 `--kv-type`、`--ubatch`（窗口里的 KV / ubatch 输入框）
仍然优先，保证用户可随时覆盖。

### 2. `auto` 的保守判定

1. 没有 NVIDIA GPU：保持 `default`，按 CPU 推理处理。
2. 上下文 `≥ 131072`：若 KV `q8_0` 的预计占用不超过整卡 95%，选 `long-context`；
   否则选 `low-vram`。
3. 其余情况：预计占用超过整卡 92% 时选 `low-vram`，否则 `default`。
4. 不根据模型标签选择策略——标签与实测收益没有稳定对应关系，避免“看起来智能但不可解释”。

本机 20.2 GB 模型 + 65K f16 KV 预计 28.2 / 31.8 GiB（88.7%），`auto` 落在 `default`；
选 128K 时自动切到 `long-context`。

### 3. 接入点

- `_llmtune.py`：纯逻辑（预设、`auto` 选择、标签映射），不依赖 Tk。
- `llmbase.Tuning` + `LaunchPlan`：策略解析后的生效值；`effective_kv_type` /
  `effective_ubatch` 按“显式 > 策略 > 档位”取值。
- `llama-server` 参数由 `LlamaCppBackend.build_argv` 统一生成，默认策略输出与原参数一致。
- CLI：`llmserve plan/start --tune ...`；窗口：启动参数区的“调优策略”下拉，
  切换后刷新硬件适配列与提示区，启动预览会打印策略与关键参数。

## 后果与边界

- 默认路径零行为变化；`auto` 只做保守切换，不会在未知环境里改变显存口径。
- `throughput` 会降低单请求速度（约 2.5%），只在确实有并发需求时使用。
- `long-context` / `low-vram` 的解码损失是显存换长度 / 容量的必然取舍，提示区会写明。
- 未纳入投机解码、`-b 8192`、`-t 24` 等“常见但本机无收益”的参数；引擎或模型变化后
  应重新跑同一套基准再调整预设。
- 基准脚本为一次性临时脚本，不进入仓库；复测时按本节方法在目标机器重跑。
