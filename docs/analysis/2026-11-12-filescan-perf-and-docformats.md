# filescan：性能二次调优 + 多文档识别 方案（只分析设计，未改代码）

- 日期：2026-11-12
- 状态：待评审
- 关联：[ADR 0019](../adr/0019-filescan.md)（D3 调度、D9 基准、D9.1/D9.2 性能结论）

> **假设**：本文把「多文档识别」理解为**支持多种文档格式的内容扫描**（docx/xlsx/pdf…），
> 而不是「一次扫描多个目录」或「批量任务」。若本意是后者，请以第 2 节的格式矩阵为准作废，
> 第 1 节性能部分仍有效。

左侧数字均为本机实测（Windows 11 / Python 3.13 GIL / 24 核 / 语料在系统临时目录），
测量脚本为一次性脚本，未进仓库；未实测的项均标注「未测」，不当结论用。

## 1. 性能：进程池之后还能挤什么

### 1.1 现状基线（同口径，`workers=4`、7 条内置规则）

| 场景 | 耗时 | 吞吐 |
|---|---:|---:|
| 5000×4 KiB（small/builtin） | 0.62 s | 8031 文件/s |
| 20×2 MiB（large/w4） | 0.89 s | 22.5 文件/s |
| 20×2 MiB（large/w1 单线程） | 2.54 s | 7.9 文件/s |

单线程 cProfile：`re.search` 56%、`_collect_matches` 自身 15%、读+open+stat 11%、
解码+splitlines 2%。下面按「能不能在剩下的 44% 里再省」逐项验证。

### 1.2 批大小 × 进程数（实测网格）

5000 个小文件，7 规则，单位秒（每格 3 次取最优；当前实现 = 上限 64 行）：

| workers \ 批上限 | 1 | 8 | 32 | 64 | 256 |
|---|---:|---:|---:|---:|---:|
| 2 | 1.097 | 0.971 | 0.942 | 0.946 | 0.949 |
| **4（现默认）** | 0.980 | 0.658 | 0.635 | **0.622** | 0.630 |
| 8 | 1.181 | 0.638 | 0.599 | 0.573 | **0.567** |
| 16 | 1.550 | 0.901 | 0.851 | 0.816 | 0.802 |

- 批上限 8 之后收益就基本榨干：8→64 只差 5%，64→256 在噪声内（±2%）。**当前 64 合理，不建议改**；
- 批上限 1（逐文件任务）比 64 慢 **58%**，真要逐文件进度必须付这个代价；
- `workers=8` 比 4 快 8%（0.573 vs 0.622），`workers=16` 反而慢 29%（超订 + spawn 成本）。
  默认 4 保持不动：24 核机器上 8 线程确实更快，但默认值改动会影响所有用户与 bench 基线，
  收益 8% 不够；用过 `--workers 8` 的用户已经能拿到。

### 1.3 子进程导入与池复用（实测）

| 项 | 实测 |
|---|---:|
| 子进程导入 `fcmd.apps.filescan._engine/_rules`（含解释器启动） | 0.106 s |
| 创建 4 进程池 + 首个任务 | 0.191 s |
| 同一进程内复用已有池再扫一遍（5000 文件） | 0.42 s（首次 0.61 s） |

- 0.19 s 的固定成本对「几千文件」量级的扫描约占 25%，对 2 小时的大目录可忽略；
- **可摊薄的地方只有 GUI**：`filescanw` 每次点「开始」都会新建进程池。改成窗口生命周期内
  复用池（首次创建后保留，关窗时 `shutdown`）可省每次 ~0.19 s。收益：GUI 重复扫描时 ~20%（小目录），
  CLI 无收益（单次进程）。风险低，但需要处理规则集变更（initializer 只在进程启动时生效，
  规则变了必须重建池）。**建议做（P2，属于 GUI 体验优化，不影响扫描语义）**。
- 进一步压导入成本（拆 fcmd 包、延迟导入）已到收益边界：0.106 s 里解释器启动就占 ~0.03 s，
  剩下是 `fcmd/__init__.py` 与两个模块，拆包会破坏现有包结构（ADR 0003），**不做**。

### 1.4 重复 stat（实测）

`walk_files` 已经 `entry.stat()` 拿到大小（用于大小过滤），`scan_file` 里又 `path.stat()` 一次：

| 项 | 实测 |
|---|---:|
| `walk_files` 5000 文件 | 34.4 ms |
| 对同一批再 `stat()` 5000 次 | 57.2 ms |

多付的 ~50 ms 占 small/builtin 的 **8%**。改法：`walk_files` 把 size 传进任务（现有 `WalkResult.sizes`
已经存了），`scan_file` 接受可选 `size` 参数，缺省仍自己 stat（单元测试与外部调用不受影响）。
**收益 8%，风险低（只改内部签名，语义不变）→ 建议做（P0）**。

### 1.5 大文件：mmap / 分块流式（实测）

2 MiB 文件、同一条匹配逻辑：

| 读法 | 耗时 |
|---|---:|
| `read()` 整读（现状） | 123.3 ms |
| `mmap` + 同样匹配 | 119.8 ms |
| 分块 256 KiB + 同样匹配 | 119.8 ms |
| 分块 1 MiB + 同样匹配 | 120.7 ms |

差异 3%，在噪声内：瓶颈是逐行正则，不是读。而且当前 `max_file_bytes` 默认 8 MiB，
`walk` 阶段就跳过了更大的文件，分块/流式只在「放宽上限后扫 100 MiB+ 单文件」时才有意义。
**收益 <3%，且会引入行边界跨块、编码跨块边界等语义风险 → 不做**。
若将来要支持超大单文件（>100 MiB 日志），再做「按字节块 + 行边界拼接」，届时单独验证。

### 1.6 规则的字面量前缀（实测，有明显例外）

内置 7 条规则里只有两条有可用字面量：`aws_key`（`AKIA`/`ASIA`）、`private_key`（`-----BEGIN`）。

| 规则 | 纯正则 | 字面量预筛 | 结论 |
|---|---:|---:|---|
| aws_key | 167.8 ms | **84.2 ms** | 2.0× |
| private_key | 27.5 ms | 68.3 ms | **更慢** |
| 7 条整体（两条都预筛） | 1496 ms | 1274 ms | **省 15%**（占整次扫描约 8%） |

原因：CPython 的 `re` 对「以字面量开头」的模式本来就有前缀跳过优化，`-----BEGIN` 已经吃到；
`aws_key` 的模式以 `\b(?:AKIA|ASIA)` 开头，`\b` 让前缀优化失效，所以手工预筛才有效。
所以不能无脑给所有规则加 `in` 判断，只有「正则里的字面量被断言/分支包裹」时才划算。

**建议**：不做通用自动推导（要解析 `sre_parse` 私有结构，风险高、易漏报），只给内置规则加一条
**显式声明**的可选字段 `prefilter: tuple[str, ...]`（命中任一子串才跑该规则），按实测只给
`aws_key` 标注。收益 8%（整次扫描），风险中低（写错=漏报，需要单测锁住「预筛后命中集合不变」）。
**建议做（P1）**；若评审认为 8% 不值维护一个语义字段，可以不做，现状不是错的。

### 1.7 worker 端结果序列化（实测）

| 结果集 | pickle 体积 | pickle 耗时 |
|---|---:|---:|
| 5000 个文件（small） | 551.5 KiB | 8.6 ms |
| 20 个文件（large） | 2.8 KiB | ~0 ms |

551 KiB / 8.6 ms 相对 622 ms 是 **1.4%**，且是一次性整批传回；继续压缩（只传命中文件、
用 tuple 代替 dataclass）最多再省 5–8 ms。**收益 <1.5%，不值得改协议 → 不做**。

### 1.8 白名单之外还能不能省 open（实测）

- 白名单外的文件在 `walk` 阶段就被跳过，**根本不会 `open`**：200 次 `open+read(1)` 实测 5.3 ms，
  即每个文件约 26 µs；mixed 场景 3000 个被跳过文件若真去打开，至少多付 ~80 ms（还没算二进制嗅探与匹配）；
- 但 `walk` 里 5000 条目仍付 41.1 ms，其中 **~30 ms 是「先 stat 再判后缀」**——被后缀挡掉的文件
  其实不需要 size。

改法：`_classify_entry` 先判后缀（`_extension_selected`），通过后再 `entry.stat()`。
收益：mixed 场景 0.53 s 里省 ~30 ms（**6%**），纯文本目录 0。风险低，唯一语义差异是被后缀跳过
且 `stat` 失败的条目会从 `errors` 归到 `skipped_extension`（统计口径变化，需要 ADR 里写一句）。
**建议做（P0）**。

### 1.9 汇总（按收益/风险排序）

| # | 改动 | 实测收益 | 风险 | 建议 |
|---|---|---:|---|---|
| 1 | 去掉重复 stat（walk 传 size） | 8% | 低 | **P0 做** |
| 2 | 后缀判断提到 stat 之前 | 6%（仅混合目录） | 低（统计口径微调） | **P0 做** |
| 3 | 内置 `aws_key` 加字面量预筛 | 8%（整次扫描） | 中低（漏报风险，需锁测） | P1 可选 |
| 4 | GUI 复用自己的进程池 | ~19%（小目录重复扫描） | 低 | P2 做 |
| 5 | 批上限/workers 调参 | ≤2% / 8%（需用户显式设 8） | 低 | 不做（现状已优） |
| 6 | mmap / 分块流式 | <3% | 中（行/编码边界） | 不做 |
| 7 | 序列化瘦身 | <1.5% | 中 | 不做 |
| 8 | 拆包压导入成本 | <5% | 高（破坏包布局） | 不做 |

P0 两项叠加预期：small/builtin 0.62 s → 约 0.53 s（+14%），mixed 0.53 s → 约 0.47 s。

## 2. 多文档识别（办公/文档格式内容扫描）

### 2.1 接入点

现有引擎是「文本文件 → 逐行匹配 → RuleMatch(行号/列区间/上下文)」。文档格式没有「行」的概念，
设计为在 `scan_file` 前增加一层**抽取**：

```
walk（白名单/魔数） → scan_file
                        ├─ 文本类：现状（读字节 → 解码 → 逐行匹配）
                        └─ 文档类：extract(path) -> list[TextUnit]（带位置）
                                     → 对每个 TextUnit 复用逐行匹配 → RuleMatch + location
```

- `TextUnit(text, location)`：`location` 是可直接给人看的位置串，例如
  `"p.12"`（PDF 页）、`"sheet:Sheet1!A12"`（Excel）、`"slide 3"`（PPT）、`"para 45"`（docx 段落序号）、
  `"header1"`（页眉）、`"comment@para 45"`（批注）；
- 抽取放在 worker 进程里做，天然复用现有进程池；抽取本身是可取消的（每 N 个部件检查一次 token）；
- `RuleMatch` 增加可选字段 `location: str = ""`，纯文本路径保持空串——**报告/CSV/JSON 向后兼容**。

### 2.2 格式矩阵（解析路径 / 依赖 / 回溯）

| 格式 | 解析路径 | 依赖 | 命中回溯 | 收益 | 成本/风险 |
|---|---|---|---|---|---|
| **docx** | `zipfile` + `xml.etree.iterparse`：`word/document.xml` 的 `w:t`（`w:tab`→`\t`、`w:br`/`w:p`→`\n`）；可选 `header*/footer*`、`comments.xml`、`footnotes/endnotes` | 标准库 | 段落序号 `w:p` 计数；页眉/批注单独标注 | 高（合同/简历/标书） | 低；实测 6 MB document.xml 抽取 125 ms（约 20 MB/s 纯文本） |
| **xlsx** | `xl/sharedStrings.xml`（去重后只扫一遍）+ 各 `xl/worksheets/sheetN.xml` 的 `inlineStr`；`workbook.xml` + `rels` 取表名 | 标准库 | 工作表名 + 行号/单元格（`r` 属性） | 高（名单/台账） | 低；实测 34 万字符 32 ms |
| **pptx** | `ppt/slides/slideN.xml` 的 `a:t`，`notesSlides` 单独标注 | 标准库 | 幻灯片序号（按文件名数字排序） | 中高 | 低；实测 60 页 14 ms |
| **odt/ods** | `zipfile` + `content.xml` 的 `text:p`/`text:h`/`table:table-cell` | 标准库 | 段落序号 / 表名+行号 | 中 | 低；实测 57 万字符 37 ms |
| **rtf** | 自写 tokenizer：跳过 `{\fonttbl...}`/`{\colortbl...}` 等控制组，处理 `\par`/`\tab`/`\'hh`/`\uN` | 标准库 | 段落序号（`\par` 计数） | 中（老合同/导出件） | 中；编码与转义分支多，需语料测试 |
| **html** | 已是白名单内的文本格式，可直接扫；增加 `html.parser` 去 `script/style` 后扫正文 | 标准库 | 行号（沿用文本路径） | 低（只是降噪） | 低；但会改变现有 html 命中结果（去标签后偏移变化）→ 需评审是否值得 |
| **pdf** | `pypdf`（文本层）/ `PyMuPDF`；按页抽 `page.extract_text()` | **可选 extra**：项目已有 `pdf` extra（`fcmd/tools/pdf/pdfbase.py` 用 `find_spec` + `lazy_import`） | 页码 `p.N` | 高（合同/报告） | 中；无文本层的扫描件只能跳过并单列统计；实现需处理加密与损坏 |
| **doc/xls/ppt（97-2003）** | OLE 复合文档（魔数 `D0CF11E0`）+ Word97/Biff8 自研解析 | **需 `olefile`**（+ 自研解析，工作量以人周计） | 段落/工作表 | 低（新文件基本是 OOXML） | 高；**不建议直接支持**，改为识别后提示「请转存为 docx/xlsx」或跳过并单列 |
| **压缩包** | `zipfile`/`tarfile`/`gzip` 下钻，成员按同一套后缀/魔数分流 | 标准库 | `a.zip!b/docx` 路径拼接 | 中（打包的合同/资料） | 中；要做嵌套深度、成员数、解压总量三重上限，防压缩炸弹 |

补充事实（实测）：
- OOXML 加密后整体变成 OLE 复合文档（首 8 字节 `D0CF11E0A1B11AE1`），`zipfile` 直接打开会失败，
  所以「加密」可以在打开前就判定，不需要先解压；
- 伪造后缀（`.txt` 实际是 zip）用魔数识别即可：`PK\x03\x04` / `%PDF-` / `{\rtf` / `D0CF11E0`；
- 压缩炸弹：20 KiB 的 docx 可解压出 20 MiB 的 `document.xml`（实测构造），**必须**按解压后大小设上限
  （本次第一个原型就是因为 `document.xml` 11 MB 超过 8 MiB 上限被跳过，行为符合预期）。

### 2.3 依赖评估

- **标准库可覆盖**：docx / xlsx / pptx / odt / ods / rtf / html / zip / tar / gz；
- **必须引入依赖**：pdf（`pypdf`，可选）、旧版 doc/xls/ppt（`olefile` + 自研，不建议）；
- 与 ADR 0019「不新增第三方依赖」的冲突只有 pdf 一处，建议沿用项目现有做法：
  加 `filescan` optional extra（`pip install fcmd[filescan]` → `pypdf`），运行时
  `find_spec` 检测，缺依赖时该格式记为 `skipped_unsupported` 并在文本报告里给出安装提示。
  **不要**把 pypdf 放进主依赖（会拖慢 `fcmd` 启动与安装体积）。

### 2.4 降级策略

| 情况 | 处理 | 统计口径 |
|---|---|---|
| OOXML 加密（OLE 容器 + EncryptionInfo） | 不解析 | `skipped_encrypted` 单列 |
| PDF 带 `/Encrypt` | 不解析（pypdf 可检测） | `skipped_encrypted` |
| PDF 无文本层（扫描件） | 已抽文本为空白 → 不当作「命中 0」 | `skipped_no_text` 单列（这是常见的「漏扫」来源，必须可见） |
| zip 损坏/截断、XML 不合法 | 记入 `errors`（现有口径），继续扫下一个文件 | `errors` |
| 单文件超限 / 解压后超限 / 部件超限 | 跳过，不中断 | `skipped_size` + 原因 |
| 缺依赖（pdf extra 未装） | 跳过 + 提示 | `skipped_unsupported` |
| 后缀与魔数不符 | 以魔数为准；都认不出时按后缀回退到文本读 | 记 `format_guess` 便于排查 |

### 2.5 上限（默认值建议）

| 项 | 默认 | 说明 |
|---|---:|---|
| 文档单文件大小 | 32 MiB | 与文本 `max_file_bytes` 分开，文档压缩率高 |
| 解压后总字节 | 256 MiB | 防压缩炸弹（实测 20 KiB→20 MiB） |
| 单个 XML 部件解压后 | 8 MiB | 超出则该部件跳过并计入 `errors`（大表常常只有 sharedStrings 超限） |
| PDF 页数 | 500 页 | 超出只扫前 500 页并标注 `truncated` |
| 压缩包嵌套深度 | 2 层 | `.zip → 内部 zip → 文档`，再深不钻 |
| 压缩包成员数 | 5000 | 超出不钻 |

全部做成 `ScanOptions` 字段（CLI/GUI 可调，默认安全），默认值写进 ADR。

### 2.6 命中位置回溯

- 每条 `RuleMatch` 带 `location`，报告在「规则 / 行号 / 上下文」之外多一列：
  `合同A.docx [sheet:Sheet1!A12 第 3 行] 手机号 …`；
- 段落/页/表的位置由抽取阶段提供，不做逆向偏移计算（文档重新排版后偏移无意义）；
- 上下文取该 `TextUnit` 内 ±`context_chars`，与文本路径一致；
- CSV/JSON 增加 `location` 字段（空值不输出，保持纯文本结果逐字节不变）。

### 2.7 白名单与统计口径改动

- 新增 `DOCUMENT_EXTENSIONS`（`.docx/.xlsx/.pptx/.odt/.ods/.pdf/.rtf`）作为**第二份白名单**，
  `ext_whitelist` 仍是文本类；文档后缀单独用 `--doc-ext-whitelist`（留空用内置，`*` 全开）；
  这样「只扫文本」的老行为不受影响，默认是否开启由评审决定（建议默认开启文档格式，语义是「扩展支持」，
  但 `--no-doc` 可一键关闭）；
- `ScanStats` 新增：`documents_parsed`、`documents_failed`、`bytes_uncompressed`、
  `files_skipped_encrypted`、`files_skipped_no_text`、`files_skipped_unsupported`；
  `_summary_line` 追加「文档 N（加密 X / 无文本 Y / 不支持 Z）」；
- 现有 `files_skipped_extension` 语义不变（后缀未命中），文档后缀命中但缺依赖 → `skipped_unsupported`，
  不混进「后缀未命中」，否则用户会误判白名单配置。

### 2.8 分阶段落地

| 阶段 | 内容 | 依赖 | 出口条件 |
|---|---|---|---|
| **P0** | 魔数识别 + docx/xlsx/pptx/odt/ods 抽取 + `location` + 上限 + 统计口径 + 单测（stdlib 合成样本） | 无 | 合成样本命中位置正确；文本路径结果逐字节不变；bench 不改动 |
| **P1** | rtf tokenizer + html 去标签（可选开关）+ 压缩包下钻（默认关） | 无 | 老 rtf 语料命中正确；压缩炸弹样本被上限挡住 |
| **P2** | PDF（pypdf 可选 extra）+ 加密/无文本层降级 + 页数上限 | `pypdf`（可选） | 缺依赖时不报错、只提示；扫描件判为 `skipped_no_text` |
| **P3** | 旧版 doc/xls/ppt | `olefile`（+ 自研） | **默认不做**；仅在明确需求下评估，预期收益低、维护成本高 |

工作量排序（相对）：P0 ≈ 4 份（五个格式共用一个 zip+XML 抽取骨架，差异只在部件名与文本标签），
P1 ≈ 2 份，P2 ≈ 1.5 份，P3 ≥ 6 份且不可控。

### 2.9 收益/成本排序（建议采纳顺序）

1. **docx + xlsx**（收益最高、纯标准库、实测抽取 20 MB/s、位置可回溯到段落/单元格）；
2. **pptx + odt/ods**（同一骨架，几乎零边际成本）；
3. **PDF**（收益高，但引入可选依赖；只做文本层，扫描件单列）；
4. **rtf**（老文档常见，需自写 tokenizer，风险中等）；
5. **压缩包下钻**（有用但必须配三重上限，且默认关闭）；
6. **html 去标签**（降噪，但会改变现有 html 命中结果，收益低）；
7. **doc/xls/ppt**（不建议做）。

## 3. 需要评审决定的三件事

1. 多文档默认开启还是 opt-in（影响统计口径与 bench 基线）；
2. 是否为 `aws_key` 这类规则引入 `prefilter` 字段（8% 收益 vs 一个语义字段的维护成本）；
3. PDF 用 `pypdf` 还是 `PyMuPDF`（项目已有两个 extra 的用法，前者纯 Python、体积小，后者快但二进制较大）。
